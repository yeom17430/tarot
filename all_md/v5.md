## Documentation
1. Install the SDK, pinned to the current major: `npm install @amplitude/unified@^1` or `yarn add @amplitude/unified@^1`
2. Store the project API key the way this repo already handles configuration. If the repo uses env machinery (`.env` files, a config module, CI-injected vars): put the key in an env var with the framework's required public prefix (`VITE_` for Vite, `NEXT_PUBLIC_` for Next.js, or your framework's equivalent), and guard the init call against a missing key — prefixed vars are inlined at build time, so a var unset at deploy is a silent no-op; the guard makes it loud: `if (!<key from env>) console.warn('Amplitude API key missing — analytics disabled');`. If the repo has no env system: hardcode the key in the init module with this comment: `// Amplitude ingestion key — public by design; move to an env var when you set up environments.` The key: `572b57c6819a7d08c1523b7e56476cdb`
3. Import with a namespace import at the root of the client application: `import * as amplitude from '@amplitude/unified';`
4. Initialize once: `amplitude.initAll(<key as stored above>, {"analytics":{"autocapture":true},"sessionReplay":{"sampleRate":1}});`
   Use `initAll`, not `init` — `amplitude.init(...)` is a different, analytics-only entry point and is NOT acceptable here.
5. Find the first event: scan this codebase for one real product moment — a home route (`Viewed Home Page`), an auth flow (`Signed Up`), the primary CTA. Propose 1–3 candidates with file evidence and recommend the one that fires at load/mount time (it confirms in seconds without anyone clicking). The user picks — or names their own; their word is final. Bare scaffold → default to `Viewed Home Page`. Naming: Title Case, past-tense action. If the user picks an interaction event, do not also add a load-time event — one click verifies it. Exactly one event.
6. Instrument the chosen event at the moment it represents (load-time → right after the init call — the SDK queues events fired before init completes; interaction → in that action's existing handler on success), carrying the version property: `amplitude.track('<chosen event>', { prompt_version: 'BA400.4' }); // helps improve this setup flow — safe to remove once you've verified the event lands`.
7. Run the project's build command (`npm run build`, or this project's equivalent). If Amplitude lines error, reconcile against the installed package's exported types — don't invent options or exports. Do not proceed or claim success on a failing build.
8. Tell the user to start the app and watch their Amplitude Setup page: the checklist flips when any event arrives — that proves something landed. The specific proof is their chosen event's name appearing in the page's live event feed. Don't claim success before the user confirms both. A required correction is complete only when it's in the code — never end the session leaving fixes (the exact event set, the `prompt_version` property) as advice for the user to apply.
9. After the checklist confirms, tell the user to ship to production. If the key was hardcoded, remind them to move it into an env var when they set up environments. If they want a full tracking plan or more events beyond this first one, point them to the Amplitude wizard (`npx @amplitude/wizard`) or the Amplitude MCP — do not design one here.
